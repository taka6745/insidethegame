# Backend and frontend review

**19 October 2026 · local hackathon scope.** Independent agents reviewed runtime correctness, code organisation, original-plan alignment, Azure configuration and official judging requirements. Findings were fixed and fresh reviewers returned no further actionable findings in those scopes. Production deployment gates remain open.

| Fixed | Why |
|---|---|
| Percentage units in answers, offers and cards | Possession must remain `30.1%`, not `30.1`. |
| Incomplete player attribution | Unknown-player actions must not produce falsely exact player totals; corrections restore availability. |
| ETL-owned recording uploads | The lab cannot silently replace its recording while upstream history and footage retain another match. |
| Active feed descriptions | Agent planning uses the current recording's semantics without leaking event history or mutating other requests. |
| Match evidence references | Model match prose requires references that exist in the current question's evidence. This validates citations, not every sentence's factual entailment. |
| Broker startup configuration | Reject the legacy Service Bus consumer when product mode is active; it is not a product delivery adapter. |
| Deployment packaging | Configurable nginx upstream/DNS, separate ETL runtime/test images, and an ETL-owned Cosmos foundation. |
| Narrow desktop cards | Stat values retain a minimum card width and scroll within their row. |

## Design assessment

Service ownership matches the active plan: ETL owns standard stats/history, the narrative service owns recap/framing, and the user backend owns questions, audiences and custom rules. Questions do not launch shared narrative generation. Models interpret bounded goals; deterministic code compiles and evaluates rules. Vendor mapping remains an adapter.

Shared calculations and bucket narratives avoid per-viewer model/event work. Static frontend delivery can scale independently. The current backend remains **one process / one match owner**: adding replicas without shared ownership, durable delivery and session coordination would be incorrect. Full-history demo checks and in-memory session handling are local harness behavior, not the proposed distributed ingestion path.

Keep [Azure deployment gates](../../terraform/deployment-readiness.md) and [hackathon readiness](hackathon-readiness.md) separate from this clean local-code review. Production brokers/stores, actual application deployment, authenticated access, operational load/recovery tests, rights clearance and judging access are still required.
