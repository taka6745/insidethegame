# Working in InsideTheGame

## What this repository is for

We are researching the Inside the Game hackathon before choosing and building our entry. Read [research/README.md](research/README.md) for the brief and [competitors/README.md](competitors/README.md) for the competitor evidence. Recommendations are provisional; follow the user's requested implementation scope.

## Product and communication preferences

- Keep the root README short: a useful overview, readable graphics, and a few links.
- Use plain descriptions of what a person can do or see. Avoid vague phrases such as “audited Azure agent pipeline.”
- Prefer graphics, compact comparisons, and expandable details to long walls of text.
- Keep folders purposeful. Use `research/` and `competitors/`; automation lives under `.github/`. Do not create an `ops/`, `docs/`, `assets/`, or root `tests/` folder just to organise a small addition.
- Favour short, reusable code and a small working product. New technology should earn its place by improving a user experience or measured result.
- Preserve local changes. Verify actual files, rendered output, data, and the GitHub workflow before calling work complete.

## Research discipline

- Use current primary sources. Link claims to the exact rules, product documentation, release, or league announcement that supports them; record when checked.
- Separate **confirmed facts**, **our interpretation**, and **proposed ideas**. Announcements and roadmaps are not proof that a feature has shipped.
- The user's working hypothesis is that this is lightweight idea/research sourcing for Microsoft and its Premier League partnership. Investigate that through incentives and product gaps; do not present an internal programme as proven or default to a marketing-only explanation.
- Assess value for Microsoft, the League, production teams, broadcasters, and fans separately. League responsibilities and club-specific responsibilities differ.
- Do not claim novelty from a feature name. Check existing products and the collected competitors, and identify the precise new behaviour or evidence we could demonstrate.
- Data-source claims need provenance. Distinguish real data, synthetic samples, runtime generators, vendor-shaped formats, and plans. A Kaggle/HF/vendor mention is not proof of dataset use.

## Building and judging

- Recheck the official rules before submission. Current research records five equal judging weights, a video under two minutes, synthetic football-realistic data, and a public entry-code repository.
- Keep this private research repository distinct from any public submission. Collected competitor files are research material; create original synthetic demo data and check licences before reusing third-party material.
- Prefer a complete ingest → interpret → explain → render → personalise experience. Include the evidence behind an explanation and a visible handling path for missing or corrected data.
- Treat deterministic calculations as functions, not pretend AI agents. Use multiple AI agents only when their distinct responsibilities and handoffs improve the outcome.
- Report measured latency, quality, and failure behaviour. Clearly label assumptions, simulated results, and proposed targets.
- Research findings and recommendations do not authorise entering the competition, accepting its terms, changing repo visibility, or submitting an entry.

## Automation and files

- The root and competitor READMEs are generated by `.github/scripts/build_report.py`. Edit the template as well as regenerating; direct edits alone may be overwritten.
- `.github/scripts/refresh.py` refreshes project metadata, repo history/LOC, collected samples, and graphics. Data and evidence live under `competitors/data/`.
- Keep credentials in ignored `.local/` files or the specifically authorised encrypted Actions secrets. Never print or commit copied authentication requests.
- Scheduled competitor refreshes run at 8 am Brisbane through 28 October 2026. The future entry's judging-access deadline is separate and later.
- Use focused verification. Tests for refresh behaviour live in `.github/scripts/test_refresh.py`; do not execute competitor application code to collect its files.
